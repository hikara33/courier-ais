# Архитектура (кратко)

## Сервисы

| Сервис | Модули | Схема БД |
|---|---|---|
| core (Ядро) | identity, couriers, orders, partners, admin, reports | core |
| dispatch (Диспетчеризация) | assignment, routing | dispatch |
| tracking (Трекинг) | ingest, broadcast, storage | tracking |
| notify (Уведомления) | messaging, webhooks | notify |

## Правила, которые нельзя нарушать

1. **Заказ меняет только модуль `orders` сервиса core.** Остальные просят его через `POST /internal/orders/{id}/assign` и т. п. Если заказ уже не «Создан» — ответ 409.
2. **Сервис ходит только в свою схему БД.** Чужие данные — через REST `/internal/...` или события.
3. **Внутри сервиса три слоя:** `api.py` → `service.py` → `repository.py`. Вверх и через слой вызывать нельзя.
4. **События** публикуются в обмен `delivery.events` (имена — `backend/common/events.py`), через таблицу outbox, потребители идемпотентны.
5. **`/internal/*` наружу не публикуется** (Nginx отдаёт 404).
6. **Тестовые заказы** (признак «тестовый») изолированы от боевых данных и отчётов.

## Клиенты и шлюз

- **Веб-панель** — статические файлы, исполняются в браузере. Nginx отдаёт их по `/` и пропускает `/v1/*` к бэкенду.
- **Мобильное приложение** — работает на телефоне, Nginx его не раздаёт; обращается к `/v1/*` и `/ws/*`.
- **Партнёры** — то же публичное `/v1/*` (модуль `partners` сервиса core), доступ по API-ключу.
- Клиенты знают только адрес шлюза. О разбиении бэкенда на сервисы они не осведомлены.
